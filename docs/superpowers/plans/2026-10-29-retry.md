# Retry Option Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After a lost race at Bob's Drive-In, offer "Retry", which reloads the state saved just before that race into the garage; off by default, switched on in the launcher.

**Architecture:** A new module `src/game/retry.c` holds the options, a silent save, a two-phase safe load (check into a buffer, then apply), the outcome classification and the dialog. The engine gets three small `RETRY:` call sites (before `race_start()`, after `race_results()`, after `bob_drive_in()`), and `flow_save.c` has its writer and loader split out of the screens without changing their behaviour. A cross build (mingw-w64) produces the Windows game and launcher.

**Tech Stack:** C11, SDL3 3.4 (Linux: system; Windows: `../deps/SDL3-3.4.18`), C++17 + wxWidgets 3.2.12 (`../deps/wx-3.2.12`), CMake + Ninja, Wine 10 for test runs, bash test scripts.

**Spec:** `docs/superpowers/specs/2026-10-29-retry-mod-design.md`

## Global Constraints

* All game state stays in `mem[]` at the original DGROUP addresses (`ENGINE.md`); `retry.c` keeps only its options, the request flag and the file buffer in C statics.
* Engine-side edits are marked `/* RETRY: ... */`.
* With `--retry` absent the game behaves exactly as the unmodified build.
* Slot files use the vanilla `HOTROD<n>.SAV` format; slots 1–16, default 16. `HOTROD1..15.SAV` and `hall_dat` are never written unless the user picks slot 1–15.
* A failed Retry never loses the current game and never calls `new_game()`.
* Jumping the light (`player_result == 0x81`) and wins are not losses. Races "just for kicks" count.
* Retry is inactive in demo mode.
* Nothing is installed on the system; third-party code only from `../deps/`.

## Review Focus

1. Slot file missing, truncated or with an over-long chain at Retry time: "Retry failed", the game continues as "Go on" with the race's normal bookkeeping (Task 3, Task 4).
2. Retry after a jail sentence: no game over, no hall-of-fame entry (Task 4).
3. Retry with a pink-slip bet lost (car already removed by `race_results`): the car is back after the load (Task 4).
4. The visible Save / Load screens behave byte-for-byte as before the refactor (Task 2).
5. The King's lost race: the King penalty (`drag_wins -= 3`, `road_wins -= 2`) is not applied after Retry (Task 4).

### Task 3: retry.c core: options, silent save, safe load, classification

**Files:**
- Create: `src/game/retry.c`, `src/game/retry.h`
- Modify: `src/main.c` (options and usage text)
- Test: `tests/retry/t3_core.sh`

**Interfaces:**
- Consumes: `flow_save_write`, `flow_load_apply`, `save_reader_mem`, `fl_save_name` (`TMPL_*` templates of `flow_save.c`; use `FLOW_STK_FNAME` as the name buffer).
- Produces (`retry.h`):
  - `void retry_set_options(bool on, int slot)` — from `main.c`; slot clamped to 1..16; forced off when the `demo` switch is given.
  - `bool retry_enabled(void)`
  - `void retry_before_race(void)` — silent save to the slot; remembers success in a static (`saved_ok`).
  - `typedef enum { RO_WON, RO_JUMPED_LIGHT, RO_POLICE, RO_JAIL, RO_LOST, RO_CRASH, RO_BREAKDOWN, RO_KING_LOST } RetryOutcome;`
  - `RetryOutcome retry_classify(s16 r)` — from `DS_player_won`, `DS_player_result`, `DS_vs_king` and `r` as in spec §4.3; `RO_KING_LOST` takes priority over the others when `vs_king && !player_won`.
  - `bool retry_check(void)` — reads the whole slot file (≤ 64 KB) into a static buffer and walks its structure: 0x24 header; car block(s) and part chains following the non-zero flags exactly as `load_car_chain`/`load_part_chain` read them; tail 8 + 0x18C + 4 + 4 + 2 bytes; the file ends exactly there; the number of cars and parts fits the pools `car_alloc` / `part_alloc` draw from (read their capacities from `garage_data.c`). Returns false on any mismatch; touches no game state.
  - `void retry_apply(void)` — applies the checked buffer: copies its first 0x24 bytes to `DS_player_name`, then `flow_load_apply` with `save_reader_mem` over the rest. Cannot fail after a passed `retry_check`; logs `retry: applied`.
  - `void retry_request(void)`, `bool retry_take_request(void)` — the C-side flag.
  - Log lines to stderr when `SR_RETRY_LOG` is set: `retry: saved slot N ok|failed`, `retry: outcome <NAME>`, `retry: check ok|failed`, `retry: applied`.

### Task 4: The offer and the engine call sites

**Files:**
- Modify: `src/game/race_bob.c` (both `race_start()` sites in `challenge()`, the block after `race_results()` in `bob_drive_in()`), `src/game/flow_main.c` (after `bob_drive_in()`), `src/game/hooks_race.c` (debug path), `src/game/retry.c`
- Test: `tests/retry/t4_offer.sh`

**Interfaces:**
- Consumes: Task 3.
- Produces: `bool retry_offer(s16 r)` in `retry.c` — returns true when the player chose Retry and `retry_check()` passed (then it has called `retry_request()`); shows "Retry failed" (the game's message box, `dialog_msg`) when the check fails; false for a win, a jumped light, Retry off, or a failed pre-race save. The dialog: the game's own style, two buttons "Retry" and "Go on", mouse and keys (R / G, Enter = Retry, Esc = Go on); the implementer picks between reusing screen 0x1E with temporarily replaced texts (restored after) or new records in an unused part of the record table.
- Call sites:
  - `challenge()`: `/* RETRY: */ if (retry_enabled()) retry_before_race();` immediately before each `race_start();`.
  - `bob_drive_in()`: right after `s16 r = (s16)race_results();` and `drv_pal_black(); opp_palette_set(-1);`: `/* RETRY: */ if (retry_offer(r)) { ui_pop(1); return; }`.
  - `game_loop` case 2: after `bob_drive_in();`: `/* RETRY: */ if (retry_take_request()) { retry_apply(); DSW(DS_game_end_flags) = 0; redraw = 1; continue; }` (skips the following `clock_hour()`).
  - `race_debug_main` drag/road path: the same two calls around `race_start()` / `race_results()`, plus `SR_RETRY_FORCE=<hex>`: after `race_start()` and before `race_results()`, set `DS_player_result` to the value and clear bit 0 of `DS_opp_result` (developer aid only).

  - forced `0x01` (lost), `0x21` (crash), `0x05` (breakdown), `0x41` (police), `0x81` (jumped light), and a won race (no force, `auto` switch): expected log `outcome` names `LOST`, `CRASH`, `BREAKDOWN`, `POLICE`, `JUMPED_LIGHT` (no dialog), `WON` (no dialog).

  - Bad file: truncate slot 16 between the save and the offer (aid `SR_RETRY_TRUNCATE=1` truncates right after the save, developer only): `check failed`, "Retry failed" shown (snapshot), no `applied`.
  - Real flow: `SR_DEBUG_RACE=bob` with a scripted challenge (click "challenge", pick drag, "just for kicks"; coordinates taken from snapshots), lose with no gas pedal, Retry: the garage screen snapshot follows (compare to a garage snapshot from a plain load).
